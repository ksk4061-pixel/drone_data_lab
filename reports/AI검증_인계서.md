# 다른 AI를 위한 검증 인계서 (드론 예측정비)

- 목적: 이 프로젝트의 작업(분석 · 모델 · 보고서 · 앱)을 다른 AI 모델이나 사람이 독립적으로 점검할 수 있게 파일 · 코드 · 과정 · 판단 근거를 정리함
- 자료는 **교육용 가상 데이터**임. 실제 부대 · 기종 정보 아님
- 작업은 AI 에이전트(Claude)가 코드를 쓰고 사용자가 요구사항 · 규칙 · 확인을 맡는 방식으로 진행함
- 이 문서의 숫자는 모두 저장소의 결과 파일에서 가져왔고, 출처 파일을 표에 적음. 점검자는 숫자를 믿지 말고 6절의 명령으로 다시 확인할 것

## 1. 요구사항과 범위
- 요구사항 원본: `README.txt`(저장소에는 올리지 않음). 요지는 정비를 마친 드론 중 **30일 안에 다시 고장 날 드론**을 예측하고, 2026-01 재점검 20대를 고르는 것임
- 제출물 3개: ① `reports/test_predictions_2025.csv`(시험 1,241건의 확률) ② `reports/분석보고서.md` ③ `reports/2026-01_드론_재점검계획.md`
- 추가로 만든 것: Streamlit 결과 앱(`app.py`), 점검 결과를 Supabase에 저장하는 탭(`store.py`), 모델 점검 B(`scripts/check_model.py`: 과거로 되돌려 채점)와 모델 점검 A(`scripts/check_features.py`: 시간 피처 전수 재계산)
- 규칙의 원본은 `AGENTS.md`임(데이터 처리 · 분석 · 검증 · 보고 규칙). 점검자는 이 규칙을 지켰는지 먼저 확인할 것

## 4. 핵심 판단과 근거 (점검자가 가장 먼저 의심해 볼 곳)
| 판단 | 이유 | 점검 포인트 |
|---|---|---|
| 정답 확인 구간(30일)이 다음 기간에 걸치는 행을 학습에서 제외 | 정답이 "정비 뒤 30일"이라 학습 행의 정답이 검증 · 시험 기간 정보를 담음. 학습 데이터의 2024-12 정비 13건이 실제로 2025년 1월 기록에 의존함 | 검증용 모델은 ≤ 2024-05-31, 시험용은 ≤ 2024-12-01로 학습했는지 |
| 시험(2025) 정답을 쓰지도 재구성하지도 않음 | 정답은 강사가 보유함 | 시험 성능은 계산하지 않았다고 보고서에 적었는지 |
| `availability_rate` 제외 | 그 달 전체 가동률이라 예측 시점에 알 수 없음. 이번 달 파일에도 없음 | `FEATURES`에 없는지 |
| 누적형 피처 제외(누적 고장 수, 누적 비행시간) | 시간이 지날수록 커져 시험 · 이번 달에서 학습 범위를 벗어남(누적 고장 수 평균: 학습 4.1, 시험 11.3, 이번 달 14.2) | 대체 피처(최근 N일 고장 수)로 성능이 유지되는지 |
| 계절 피처 제외 | 검증 PR-AUC 개선이 선택 기준(0.005)에 못 미침(0.001) | 선택 규칙이 결과를 보기 전에 정해졌는지 |
| 월 20대 후보 = 달마다 드론별 가장 최근 정비 기록 | 업무상 한 달에 드론 20대를 고르므로 같은 드론이 두 번 후보가 되지 않게 함 | 채점 방식(강사)이 행 기준이면 적중 수가 달라질 수 있음 |
| 위험 표시 기준은 검증 기간에서만 선택 | 시험으로 고르면 안 된다는 규칙 | `artifacts/threshold_cost.csv`가 검증 행으로만 계산되는지 |
| 점검 결과 표에 RLS 켬, SQL은 매개변수 | 공개 앱 + 외부 DB이므로 공개 API 키로 접근 막고 주입 방지 | `store.py` |

## 6. 재현 방법 (Windows PowerShell)
저장소를 받은 뒤 **강의 원본 데이터 3개(`drone_train.csv` · `drone_test.csv` · `drone_this_month.csv`)를 `data/`에 넣어야 함**(저장소에 없음).
```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python scripts/eda.py            # 처리 건수 · 패턴 · 정답 정의 검증
python scripts/train.py          # 검증 · 기준 선택 · 시험 예측 (결과가 결정적이라 재실행해도 같아야 함)
python scripts/score.py          # 이번 달 순위
python scripts/check_model.py    # 모델 점검 B (6개 점검의 합격 기준은 스크립트 맨 위에 있음)
python scripts/check_features.py # 모델 점검 A (5개 점검, 원본 data/ 필요)
python scripts/make_reports.py   # 보고서 생성 + 제출 결과 대조
```
- 데이터가 없으면 `eda.py` · `train.py`는 실행할 수 없음. 이 경우에도 `artifacts/` · `reports/`의 결과 파일과 `app.py`로 숫자 일관성은 점검할 수 있음
- 재실행 뒤 `reports/test_predictions_2025.csv` · `artifacts/model_card.json`이 기존과 **바이트 단위로 같아야 함**(작업 중 한 번 이렇게 확인함)

## 7. 점검자가 확인할 체크리스트
**데이터 처리 · 누수**
1. `drone_lib.clean`이 `AGENTS.md`의 처리 기준과 일치하는가(행 삭제 없음, 원본 불변)
2. `add_time_features`가 이번 정비일 **이후** 기록을 쓰지 않는가. 경계 사례: 정확히 90일 전, 같은 날, 첫 기록. (점검 A가 전수 재계산으로 이미 확인했으나 **정의 해석 자체**는 같은 사람이 구현했으므로 점검자가 정의를 따로 판단할 것)
3. 시험 · 이번 달 피처가 학습 → 시험 → 이번 달 기록을 이어서 계산하는가(`load_all`)
4. `FEATURES`에 `availability_rate` · `equipment_id` · `unit_code` · `maintenance_date` · `fault_code`가 없는가
5. 학습 · 검증 · 시험 기간이 겹치지 않고, 정답 확인 구간이 걸치는 행이 빠졌는가(`scripts/train.py`)

**평가 · 기준**
6. 위험 표시 기준이 검증 행으로만 정해졌는가. 300 · 600만원 비교가 맞는가
7. PR-AUC와 월 20대 적중이 기준선(무작위 · 오래된 순)과 함께 보고됐는가. 정확도만 보고하지 않았는가
8. 보고서의 모든 숫자가 `check_model.py` B1처럼 별도 코드로 재계산되는가

**제출물 · 보고서**
9. `test_predictions_2025.csv`: 1,241행, 열 `equipment_id, maintenance_date(YYYY-MM-DD), prob(0~1)`, `drone_test.csv`의 키와 일치
10. 보고서가 시험 성능을 계산하지 않았다고 정직하게 적었는가, 한계 문구가 `model_card.json`의 `limits`와 같은가

**앱 · 보안**
11. `store.py`의 SQL이 모두 매개변수 방식인가, 표 생성 시 RLS를 켜는가, 입력 길이 · 값 검증이 있는가
12. 저장소(커밋 이력 포함)에 연결 주소 · 비밀번호가 없는가: `git log -p | grep -E "pooler\.supabase|password"`
13. `app.py`의 보고서 탭이 저장소 내부 HTML만 iframe으로 여는가(외부 입력 없음)

## 8. 알려진 한계 · 미해결 · 점검 중 발견한 것
- **B3 주의**: 단순 규칙(최근 정비가 사후 · 긴급인 드론부터, 최근 90일 고장 수 많은 순)이 월 20대 적중에서 모델보다 2대 많음(39 대 37). 월별 표본이 작아 우연일 수 있으나, "상위 20대 선정" 용도에서 모델의 우월성은 입증되지 않음. 행 단위 PR-AUC는 모델 0.789, 규칙 0.775
- **시험(2025) 성능 미점검**: 정답이 없음. 시험 성능은 강사 채점으로만 확인 가능
- **검증 성능이 낙관적일 수 있음**: 피처 묶음과 위험 표시 기준을 같은 검증 기간에서 골랐음. 걸어가며 재학습(B6)으로 영향을 줄여 봤으나 피처 선택은 분리되지 않음
- **보정**: 0.3~0.4 구간에서 실제(0.474)가 예측(0.352)보다 높음. 0.7~0.8 구간은 건수 12건이라 판단 보류
- **이번 달 모델은 정답이 있는 2024-12까지만 학습함**: 2025년 기록은 정답이 없어 쓰지 못함
- **정비를 극단적으로 자주 하는 드론**(DR-0115는 3년간 151회, 134회가 고장 정비): 시간 피처가 학습 범위 끝에 몰려 확률이 매우 높게 나옴
- **점검 A의 독립성 한계**: 별도 코드(pandas 없이 csv · datetime)로 전수 재계산했지만 같은 사람(AI)이 같은 정의 해석으로 구현함. 구현 오류는 잡지만 정의 해석 오류(예: 이번 정비를 고장 수에 포함하는 것이 업무에 맞는지)는 잡지 못함. 점검자가 정의를 따로 검토할 것
- **근거 기록 공개 범위**: 원본 `data/`는 저장소에 없고, 앱의 점검 A 탭은 대상 20대의 고장 정비 일자 · 구분 · 피처 값만 `artifacts/trace_targets.json`으로 보여 줌
- **자동 시험 코드가 저장소에 없음**: Supabase 저장 시험, 점검 집계 시험, 화면 캡처 도구는 임시 폴더에서 실행했고 저장소에 포함하지 않음. 점검자가 재실행할 수 있는 형태가 아님
- **배포 상태**: 원격에는 `a6cd1e9`까지 올라가 있고 모델 점검 B(`cc72e55`)와 점검 A, 이 인계서는 아직 push하지 않음. `.streamlit/config.toml`에 끝 줄바꿈 한 줄 차이가 커밋되지 않은 채 남아 있음(내용 영향 없음)
- **비밀 값 이력**: 작업 중 DB 연결 비밀번호가 한 번 채팅 화면에 노출됐으나 저장소에는 올라가지 않음(이력 검색으로 확인). 노출된 비밀번호는 변경을 권장함
